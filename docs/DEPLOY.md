# Развёртывание системы на сервере

Локально система работает по адресу `localhost`, и показать её кому-то
кроме себя нельзя. Для защиты курсовой работы нужен постоянный адрес:
методические указания прямо просят приложить ссылку на развёрнутое
приложение в разделе «Демонстрация работы».

Ниже — что уже готово в репозитории и что нужно сделать руками.

---

## Что уже готово

| Файл | Назначение |
|---|---|
| `Dockerfile` | Собирает образ: ставит зависимости, копирует код, сайт и модель |
| `requirements-runtime.txt` | Только то, что нужно на сервере — без CatBoost, FastAPI и pytest |
| `docker-compose.yml` | Запуск того же образа локально, чтобы проверить перед отправкой |
| `.dockerignore` | Не пускает в образ данные, документацию и служебные файлы |
| `amvera.yaml` | Конфигурация для площадки Amvera: порт приложения |
| `scripts/healthcheck.py` | Проверка живости, по ней платформа понимает, что приложение работает |

Запускается `scripts/serve.py` — он отдаёт и сайт, и программный
интерфейс с одного адреса. Это важно: страница обращается к API по тому
же адресу, откуда загружена, поэтому ничего настраивать не нужно.

**Модель едет в образ вместе с кодом.** Каталог `models/global/` теперь
не исключён из репозитория — иначе на сервере не оказалось бы обученной
модели и прогноз считался бы по статистике.

---

## Вариант 1. Amvera Cloud — рекомендуемый

Российская площадка: оплата обычной картой, развёртывание через `git push`,
бесплатный поддомен с сертификатом. При регистрации даётся 111 ₽ на
пробу, тариф начинается от 170 ₽ в месяц — этого хватает с запасом.

### Шаги

1. Зарегистрироваться на `amvera.ru`.

2. В личном кабинете: **Создать проект** → тип **Приложение** →
   имя, например `warehouse`.

3. Выбрать способ доставки кода — **Через Git**. Платформа покажет
   адрес репозитория вида `https://git.amvera.ru/<логин>/warehouse`.

4. Локально, в папке проекта, добавить этот адрес как ещё один
   удалённый репозиторий и отправить код:

   ```bash
   git remote add amvera https://git.amvera.ru/<логин>/warehouse
   git add -A
   git commit -m "Подготовка к развёртыванию"
   git push amvera master
   ```

   Если ветка называется `main`, команда будет `git push amvera main:master`.

5. Платформа сама найдёт `Dockerfile`, соберёт образ и запустит
   контейнер. Сборка идёт 3–7 минут, за ней можно следить в разделе
   **Журналы** личного кабинета.

6. В разделе **Настройки** включить доменное имя. Приложение получит
   адрес вида `warehouse-<логин>.amvera.io`.

### Если сборка не прошла

- **«не найден Dockerfile»** — проверьте, что файл лежит в корне
  репозитория и отправлен в Amvera, а не только закоммичен локально.
- **Приложение собралось, но адрес не отвечает** — в `amvera.yaml`
  должно стоять `containerPort: 8000`. Платформа по умолчанию ждёт
  порт 80 и стучится не туда.
- **Не хватило памяти при сборке** — поднимите тариф на время сборки,
  потом верните обратно.

## Вариант 2. Обычный VPS

Подходит, если нужен полный контроль либо если в записке хочется
описать развёртывание на виртуальном сервере. Цена у российских
провайдеров начинается примерно от 200–450 ₽ в месяц.

```bash
# на сервере, под Ubuntu
sudo apt update && sudo apt install -y docker.io docker-compose-plugin git
git clone <адрес вашего репозитория> warehouse && cd warehouse
sudo docker compose up -d --build
```

Приложение поднимется на порту 8000. Дальше нужно закрыть его
обратным прокси, чтобы работал обычный адрес и сертификат:

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
```

Конфигурация `/etc/nginx/sites-available/warehouse`:

```nginx
server {
    server_name ваш-домен.ru;

    client_max_body_size 30M;   # загрузка файлов до 25 МБ

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 180s;   # дообучение модели занимает секунды
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/warehouse /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d ваш-домен.ru
```

Два параметра здесь существенны. `client_max_body_size` — иначе nginx
отклонит выгрузку крупнее одного мегабайта своей ошибкой, и пользователь
увидит непонятное сообщение. `proxy_read_timeout` — обработка файла с
дообучением модели занимает до 30 секунд, а стандартного таймаута
в 60 секунд может не хватить при большом файле.

## Проверка перед отправкой

Собрать и запустить образ локально — если здесь работает, на площадке
поведение будет тем же:

```bash
docker compose up --build
```

Открыть `http://localhost:8000`, загрузить `data/demo_3years_20products.xlsx`
и убедиться, что:

- виден индикатор с этапами обработки;
- появился отчёт об очистке и сообщение о проверке модели;
- кнопка «Рассчитать» выдаёт экономический эффект.

Отдельно проверить, что модель действительно попала в образ:

```bash
curl http://localhost:8000/health
```

В ответе должно быть `"model_loaded": true`. Если там `false` — модель
не доехала: проверьте, что `models/global/` есть в репозитории.

## Если модель обучали с CatBoost

`requirements-runtime.txt` намеренно не содержит CatBoost: он весит
сотни мегабайт, а сохранённая модель читается средствами scikit-learn.
Но если вы переобучите модель на машине, где CatBoost установлен, она
сохранится в его формате и на сервере не загрузится — система молча
перейдёт на статистический прогноз.

Проверить формат:

```bash
python -c "import json; print(json.load(open('models/global/meta.json'))['backend'])"
```

Должно быть `sklearn`. Если там `catboost`, есть два пути: переобучить
в окружении без CatBoost либо добавить строку `catboost>=1.2`
в `requirements-runtime.txt` и смириться с размером образа.

## После развёртывания

Полученный адрес нужно вписать в пояснительную записку, в пункт
«Демонстрация работы»: методические указания просят ссылку на
развёрнутое приложение. Там же в анализе эффективности проекта строку
«Развёртывание на сервере — не выполнено» следует поменять на
«выполнено».
