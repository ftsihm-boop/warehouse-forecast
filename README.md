# Система интеллектуального управления складскими запасами

Прогноз спроса и автоматический расчёт закупки. Менеджер загружает выгрузку
продаж из кассы или 1С и получает ответ на единственный вопрос, который его
занимает: **что, сколько и когда заказать** — с денежной оценкой того, что
это даст по сравнению с нынешним способом планирования.

**Работающая система: https://warehouse-geekdup.amvera.io**

Загрузите туда `data/demo_auto_3years_20products.xlsx` из этого репозитория —
или свою выгрузку продаж. Ничего настраивать не нужно: колонки распознаются
сами, модель дообучается под ваш ассортимент прямо при загрузке.

---

## Что система делает

1. Читает выгрузку в любом виде: CSV, XLSX, отчёт 1С со служебными строками
   над шапкой. Сама находит колонки по словарю синонимов.
2. Чистит данные: дубли, возвраты, пропущенные даты, выбросы. Отдельно
   размечает дни дефицита — когда продажи нулевые из-за отсутствия товара,
   а не из-за отсутствия спроса.
3. Разделяет ассортимент по предсказуемости спроса и честно говорит, каким
   товарам прогноз не поможет.
4. Строит прогноз на горизонт планирования — не одно число, а медиану и
   верхнюю границу, из разницы которых получается страховой запас.
5. Считает точку заказа и рекомендуемый объём закупки по каждой позиции.
6. Оценивает экономический эффект бэктестом на фактических продажах: прогоняет
   историю дважды — как если бы закупками управляли вручную и как это делает
   система — и сравнивает суммарные затраты.
7. Выгружает заявку на закупку в Excel — документ, который менеджер передаёт
   в снабжение или на согласование.

Последний пункт — главный. Система не просто прогнозирует, она доказывает
цифрой, что от неё есть польза, и одинаково готова сказать, что пользы нет.

## Быстрый старт

```bash
pip install -r requirements.txt
python scripts/serve.py
```

Дальше открыть `http://localhost:8000`. Сервер написан на стандартной
библиотеке и отдаёт сайт и программный интерфейс с одного адреса, поэтому
настраивать ничего не требуется.

Нужны данные для пробы — в репозитории лежат два готовых файла, по три года
истории и 20 товаров в каждом:

```bash
python scripts/make_demo_xlsx.py                  # продуктовый магазин
python scripts/make_demo_xlsx.py --domain auto    # автозапчасти
```

Обучение модели на своих данных:

```bash
python -m src.train --data <ваш файл> --out models/global
```

Тесты: `pytest -q` либо `python tests/test_pipeline.py` — 42 теста,
работают и без pytest.

## Архитектура

Трёхуровневая клиент-серверная схема. Расчётные модули не знают, кто их
вызывает: одни и те же функции используются сайтом, скриптами командной
строки и тестами.

```
файл (xlsx / csv / выгрузка 1С)
   │
   ├─ ingest.py        поиск шапки, синонимы колонок, разбор типов
   ├─ cleaning.py      очистка, цензурированный спрос, отчёт
   ├─ demand_classes.py отбор товаров, пригодных для прогноза
   │
   ├─ features.py      признаки; target = сумма за горизонт / (среднее28 × горизонт)
   ├─ model.py         квантили 0.5 и 0.9
   ├─ model_fit.py     проверка на данных пользователя и дообучение
   │
   ├─ inventory.py     страховой запас, точка заказа, объём заказа
   ├─ economics.py     экономика по каждому товару из его цен
   └─ backtest.py      as-is против to-be, экономический эффект
```

Схемы в формате изображений — в `docs/diagrams/`, генерируются скриптом
`python scripts/make_diagrams.py`.

### Два решения, без которых ничего не работает

**1. Модель не знает, что за товар она предсказывает.** В признаках нет
`sku`, `item_id` и категории — только форма ряда. Поэтому модель, обученная
на продуктах, применима к автозапчастям.

**2. Предсказывается множитель, а не штуки.**

```
target = (сумма продаж за горизонт) / (среднее за 28 дней × горизонт)
```

Товар с 5 шт/день и товар с 500 шт/день после нормировки для модели
одинаковы. Обратно умножаем при выдаче. Без этого перенос на чужие данные
не работает: модель выучит масштабы обучающей выборки.

**Целевая величина — сумма за горизонт, а не продажи конкретного дня.**
Точно предсказать, сколько масла купят 14 ноября, невозможно; «за следующие
30 дней уйдёт 480–540 литров» — реально, и именно это нужно для расчёта
заказа. Дневная раскладка для графика строится отдельно, по профилю дня
недели.

### Режим прогноза выбирается по каждому товару

| История | Режим | Что происходит |
|---|---|---|
| ≥ 180 дней | `fine_tune` | Глобальная модель дообучается на данных этого товара |
| 60–179 дней | `global` | Предобученная модель как есть |
| 14–59 дней | `stats` | Скользящее среднее и перцентиль, в интерфейсе честная плашка |
| < 14 дней | `reject` | Отказ с объяснением |

## Очистка данных: пять слоёв

**Слой 1 — структура.** Синонимы колонок (`Номенклатура`, `item_cnt_day`,
`Продано, шт.`), поиск строки шапки в первых 20 строках: выгрузки 1С кладут
сверху 3–5 служебных строк, и это типовая причина ошибки «колонки не
найдены». Выбирается лист с наибольшим числом распознанных колонок.

**Слой 2 — типы.** Даты: Excel serial (`45890`), ISO, `31.12.2025`,
`31/12/25`, «31 декабря 2025». Числа: `1 234,56`, `1,234.56`, неразрывный
пробел, `12 шт`, `—`, `н/д`.

**Слой 3 — логика.** Возвраты (отрицательные продажи) обнуляются с флагом.
Дубли «дата + товар» суммируются. Похожие наименования («Фильтр масляный» и
«Фильтр масляный ») склеиваются. Пропущенные даты дозаполняются нулями: для
временного ряда отсутствие строки означает «продали 0», а не «нет данных».
Выбросы винзоризуются, а не удаляются.

**Слой 4 — цензурированный спрос.** День, когда продажи равны нулю **и**
остаток равен нулю, — это не «спроса не было», а дефицит: спрос был, товара
не было. Если скормить такие дни модели как честные нули, она научится
систематически занижать спрос и система начнёт усугублять дефицит вместо
того чтобы его лечить. Такие дни помечаются и исключаются из обучения.

**Слой 5 — отчёт.** Машиночитаемый для интерфейса и текстовый для выгрузки.

## Страховой запас: квантили вместо коэффициента 1,65

Учебная формула `SS = 1.65 × σ × √L` предполагает нормальное распределение
спроса, которого у штучных товаров нет и близко: много нулей, редкие
всплески, асимметрия. Вместо этого обучаются две модели — на квантиль 0.5
и 0.9 — и страховой запас берётся как их разность:

```
SS  = q90(спрос за L) − q50(спрос за L)
ROP = q50(спрос за L) + SS
Q   = q90(спрос за L + R) − остаток − товар в пути
```

Распределение берётся из самих данных, а не из предположения о его форме.

---

## Метрики: WAPE, а не только MAPE

`MAPE = mean(|y − ŷ| / y)` взрывается при y около нуля: день с продажей
1 шт и прогнозом 3 шт даёт вклад 200 %. У сезонных товаров таких дней много.
`WAPE = Σ|y − ŷ| / Σy` устойчив к нулям и читается как «ошиблись на N % от
оборота». Считаются обе.

Отдельно измеряется **покрытие q90** — доля фактов, уложившихся под верхнюю
границу прогноза. Это самая важная и самая неочевидная метрика: модель может
прекрасно угадывать средний спрос и при этом давать слишком узкий интервал,
и тогда страхового запаса систематически не хватает.

## Автоматический отбор товаров: классификация спроса

Не всякий товар поддаётся прогнозированию. Масло моторное продаётся каждый
день примерно одинаково; турбокомпрессор — «0, 0, 0, 0, 1, 0, 0, 0, 2».
Модель, которой скормили второй ряд, увидит редкий всплеск и заложит
страховой запас «на такой случай» — деньги замораживаются, экономический
эффект уходит в минус.

Ручной порог по среднему объёму («брать товары от N шт/день») задачу не
решает: товар может продавать 6 шт/день в среднем и при этом две трети дней
простаивать.

Используется классификация Синтетоса–Бойлана по двум показателям:

- **ADI** — средний интервал между продажами (регулярность),
- **CV²** — квадрат коэффициента вариации размера продажи (стабильность объёма).

| | CV² < 0.49 | CV² ≥ 0.49 |
|---|---|---|
| **ADI < 1.32** | `SMOOTH` — прогноз моделью | `ERRATIC` — модель и увеличенный запас |
| **ADI ≥ 1.32** | `INTERMITTENT` — агрегат за горизонт | `LUMPY` — прогноз неприменим, min/max |

Класс выводится бейджем у каждого товара, а непригодные позиции
исключаются из расчёта экономического эффекта — не ради красивой цифры,
а потому что мерить систему на товарах, которые она не берётся
прогнозировать, нечестно. Число исключённых позиций показывается рядом.

## Экономика из данных

Если в выгрузке есть цена продажи и закупочная цена, маржа, стоимость
хранения и упущенная прибыль считаются по реальным цифрам магазина, а не по
усреднённым допущениям. Каждый товар получает свою экономику.

Сколько держать страхового запаса — не вопрос вкуса, у него есть точный
ответ, и он выводится из экономики товара по модели газетчика:

```
Cu = цена продажи − закупочная цена          цена нехватки
Co = закупка × ставка хранения × дни / 365    цена излишка
critical_ratio = Cu / (Cu + Co)               оптимальный уровень сервиса
```

Товар с высокой наценкой и дешёвым хранением автоматически получает больший
страховой запас, товар с низкой наценкой — меньший. Пользователь не
настраивает ничего.

### Почему коэффициент подбирается по каждому товару, а не один на всех

Сначала подбирался один коэффициент на весь ассортимент. Это оказалось
грубой ошибкой.

Подбор искал число, которое устроит сразу все товары. Но если хотя бы по
одному товару прогноз не работает — например, сезонный товар, которого
модель не видела, — дефицит по нему не закрывается никаким запасом. Подбор
честно пытался его закрыть и поднимал коэффициент **глобально**: 1.3 → 2.2
→ 3.7. Проблемному товару это не помогало, а все остальные получали тройной
запас и тонули в стоимости хранения.

Замер на одних и тех же данных и с одной и той же моделью:

| Способ подбора | Коэффициент | Эффект в месяц |
|---|---|---|
| Единый, теоретическое значение | × 1,27 | **+8 425 ₽** |
| Единый, выбранный прежним алгоритмом | × 3,73 | **−6 451 ₽** |
| Потоварный (реализовано) | от × 0,30 до × 1,49 | **+9 091 ₽** |

Разница только в способе выбора запаса. Система с точным прогнозом
(WAPE 9,5 %) показывала убыток.

Теперь этим занимается `backtest.tune_portfolio()`: коэффициент ищется
вокруг теоретического оптимума **каждого товара**, прогноз считается один раз
на товар и переиспользуется для всей сетки, а если по товару даже лучший
коэффициент проигрывает ручному правилу — товар остаётся на ручном
планировании, называется в отчёте и в эффект не засчитывается.

Последнее принципиально: система обязана знать границы своей применимости.
Честное «по этим товарам мой прогноз бесполезен, закупайте их как раньше»
ценнее натянутого на весь ассортимент убыточного результата.

## Модель дообучается на каждом загруженном файле

Главная проблема любой предобученной модели: её учили на одном ассортименте,
а пользователь загружает другой. Внешне всё работает, прогноз считается, но
он систематически смещён — и обнаруживается это только в экономическом
расчёте.

При загрузке файла система отрезает последние 45 дней, прогнозирует их
моделью и сравнивает с фактом. Оценивается три величины:

| Метрика | Что показывает | Порог |
|---|---|---|
| WAPE | величина ошибки | ≤ 35 % |
| Смещение | систематический перекос | ≤ 12 % |
| Покрытие q90 | доля фактов под верхней границей | ≥ 80 % |

**Дообучение запускается всегда, а не только при провале проверки.** Раньше
было иначе, и это оказалось ошибкой: проверка отвечает на вопрос «насколько
точен прогноз», но не на вопрос «выгодно ли по нему закупать». Модель с
ошибкой 9,5 % спокойно проходила проверку и при этом теряла деньги — её
доверительный интервал был откалиброван под чужой ассортимент.

Обучение идёт только на части истории до проверочного окна, а сравнение
«стало лучше или хуже» — на окне, которого не видела ни исходная модель, ни
дообученная. Если лучше не стало, возвращается исходная: предсказуемое
поведение важнее попытки улучшить любой ценой.

**Измеренный эффект.** Модель, обученная на заведомо чужом ассортименте,
проверена на демонстрационном файле:

| | Эффект в месяц |
|---|---|
| было: единый коэффициент, без дообучения | **−3 598 ₽** |
| потоварный подбор | **+2 945 ₽** |
| потоварный подбор и дообучение | **+3 564 ₽** |

## Демонстрационные данные

Два файла по три года истории и 20 товаров, генерируются скриптом:

```bash
python scripts/make_demo_xlsx.py                  # продуктовый магазин
python scripts/make_demo_xlsx.py --domain auto    # автозапчасти
```

Области намеренно устроены по-разному. У продуктов недельный пик в
пятницу-субботу и всплески перед праздниками; у автозапчастей суббота тоже
сильная, но воскресенье проваливается, а в сами праздники торговля почти
останавливается — зато растёт перед ними. Сезонность у продуктов мягкая,
у автотоваров жёсткая: зимние шины летом не продаются вовсе (отношение
пикового месяца к провальному — 55 раз).

В обоих файлах присутствуют все четыре класса спроса, дни дефицита,
промо-акции и рост цен со временем.

Проверка переноса на незнакомый ассортимент: модель, обученная на продуктах,
на файле автозапчастей даёт WAPE 19,6 % и смещение +8,0 %; после
дообучения при загрузке — 15,4 % и −1,2 %.

## Сайт

`scripts/serve.py` отдаёт и сайт, и API с одного адреса. `api/main.py`
(FastAPI) остаётся для промышленной эксплуатации: логика общая, оба сервера
вызывают одни и те же функции из `src/`.

**Сайт работает и без сервера.** Если модель недоступна, страница честно
пишет об этом и считает прогноз сама, упрощённой формулой — её можно открыть
двойным щелчком и показать где угодно без установки. Это не запасной вариант
на всякий случай, а осознанный режим демонстрации.

| | Без сервера | С сервером |
|---|---|---|
| Прогноз | среднее за окно | градиентный бустинг |
| Страховой запас | норматив 1,65σ | доверительный интервал и экономика товара |
| Очистка данных | базовая | пять слоёв и отчёт на экране |
| Классы спроса | нет | бейдж у каждого товара |
| Экономический эффект | нет | бэктест на фактических продажах |

Адрес API определяется автоматически: тот же хост, откуда открыта страница,
либо `localhost:8000` для файла. Переопределяется параметром в адресной
строке: `index.html?api=http://192.168.1.50:8000`.

Интеграция вносится в вёрстку скриптом `scripts/patch_web.py`. Он
идемпотентный и умеет обновлять уже внесённые правки, поэтому дизайн сайта
можно менять, просто положив новую версию в `web/index.html`.

| Метод | Адрес | Что делает |
|---|---|---|
| POST | `/upload` | файл → `session_id`, очистка, дообучение модели |

## Заявка на закупку

Рекомендация системы бесполезна, пока она остаётся на экране: её нужно
передать в снабжение, согласовать у руководителя, отправить поставщику.
Кнопка «Скачать заявку на закупку» отдаёт для этого не дамп таблицы, а
документ из трёх листов:

| Лист | Что внутри |
|---|---|
| Заявка на закупку | Только позиции, которые нужно заказать: срочность, остаток, дата исчерпания, количество, цена, сумма. Итог по заявке и место для подписей |
| Полный план | Все товары со статусами, прогнозом, страховым запасом и точкой заказа — для контроля |
| Параметры расчёта | Источник данных, результаты очистки, горизонт и срок поставки, метрики модели |

Третий лист принципиален: документ уходит из системы и должен быть
самодостаточным. Через месяц никто не вспомнит, при каком сроке поставки
считалась заявка, — и без этих сведений её будут пересчитывать вручную.

Стоимость позиции и итог записаны **формулами Excel**, а не готовыми
числами: снабженец может округлить количество до кратности упаковки прямо
в файле, и сумма пересчитается сама.

Заявку собирает сервер — тем же кодом, который считает план на экране.
Если бы файл собирался отдельно, цифры на экране и в документе со временем
разошлись бы.

## Развёртывание

Система развёрнута и доступна по адресу **https://warehouse-geekdup.amvera.io**.

```bash
docker compose up --build       # локальная проверка того же образа
```

Образ собирается по `Dockerfile`: ставятся только зависимости, нужные на
сервере, копируются расчётные модули, сайт и обученная модель. Приложение
работает от непривилегированного пользователя.

В сборку встроена проверка `scripts/verify_model.py`: она пытается прочитать
обученную модель и обрушивает сборку, если формат модели не соответствует
установленным библиотекам. Без неё несоответствие проявилось бы не при
сборке, а на работающей системе — прогноз молча считался бы упрощённым
статистическим методом.

Подробная инструкция, включая настройку обратного прокси и подводные камни
с форматом модели, — в [`docs/DEPLOY.md`](docs/DEPLOY.md).

## Откуда брать обучающие данные

| Источник | Что внутри | Регистрация | Подготовка |
|---|---|---|---|
| **[Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii)** | 1,07 млн строк реальных продаж британского интернет-магазина, 2009–2011, с ценами | не нужна | `scripts/prepare_online_retail.py` |
| [Predict Future Sales (1С)](https://www.kaggle.com/competitions/competitive-data-science-predict-future-sales/data) | 2,9 млн строк, 60 магазинов, российские данные | нужна | `scripts/prepare_1c.py` |
| [Store Item Demand](https://www.kaggle.com/c/demand-forecasting-kernels-only/data) | 10 магазинов × 50 товаров, 5 лет, очень ровные ряды | нужна | как канонический CSV |

Обучение сразу на нескольких источниках:

```bash
python scripts/train_multi.py \
    --data data/online_retail_canonical.parquet data/1c_canonical.parquet \
    --out models/global --balance
```

Отдельно проверялось, заменяет ли обучение на нескольких источниках
дообучение под пользователя. Не заменяет: модель, обученная на трёх разных
наборах, на незнакомых данных показала то же покрытие интервала и
отрицательный эффект. После дообучения оба варианта сошлись к одному
результату. Вывод для практики: **дообучение на данных пользователя важнее
разнообразия обучающей выборки**, и именно оно включено по умолчанию.

## Тестирование

42 модульных теста: чтение файлов, очистка, отсутствие утечки будущего в
признаки, расчёт запаса, классификация спроса, экономика, проверка и
дообучение модели. Интерфейс отдельно проверяется в браузере через
Playwright — включая отрицательный сценарий, когда система должна сообщить
о невыгодности внедрения.

```bash
pytest -q
```
