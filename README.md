# Система интеллектуального управления складскими запасами

Прогноз спроса и автоматический расчёт закупки. Менеджер загружает выгрузку
продаж из кассы или 1С — получает список «что, сколько и когда заказать».

## Быстрый старт

```bash
pip install -r requirements.txt

# 1. сгенерировать тестовые данные (чистые и специально испорченные)
python scripts/make_synthetic.py --days 730 --out data/clean.csv
python scripts/make_synthetic.py --days 730 --messy --header-1c --out data/messy.xlsx

# 2. обучить глобальную модель
python -m src.train --data data/clean.csv --out models/global

# 3. прогнать весь пайплайн от очистки до бэктеста
python scripts/run_demo.py --data data/messy.xlsx

# 4. поднять API для веб-интерфейса
uvicorn api.main:app --reload --port 8000
```

Тесты: `pytest -q` или `python tests/test_pipeline.py` (работает без pytest).

### Гибридная схема (вариант C)

Режим выбирается **по каждому товару отдельно**, а не по файлу целиком:

| История | Режим | Что происходит |
|---|---|---|
| ≥ 180 дней | `fine_tune` | Глобальная модель дообучается на данных пользователя (`init_model` в CatBoost) |
| 60–179 дней | `global` | Предобученная модель как есть |
| 14–59 дней | `stats` | Скользящее среднее + перцентиль, в интерфейсе честная плашка |
| < 14 дней | `reject` | Отказ с объяснением |

### Два решения, без которых гибрид не работает

**1. Модель не знает, что за товар она предсказывает.**
В признаках нет `sku`, `item_id`, `category` — только форма ряда. Поэтому
модель, обученная на дисках 1С, применима к молоку.

**2. Предсказываем множитель, а не штуки.**

```
target = (сумма продаж за горизонт) / (среднее за 28 дней × горизонт)
```

Товар с 5 шт/день и товар с 500 шт/день после нормировки для модели
одинаковы. Обратно умножаем при выдаче. Без этого перенос на чужие данные
не летит: модель выучит масштабы обучающей выборки.

**Бонус: целевая — сумма за горизонт, а не значение конкретного дня.**
Точно предсказать, сколько молока продадут 14 ноября, невозможно;
«за следующие 30 дней уйдёт 480–540 литров» — реально, и именно это нужно
для расчёта заказа. Дневная раскладка для графика делается отдельно,
по профилю дня недели (`forecast_curve`).

## Очистка данных: пять слоёв

**Слой 1 — структура.** Синонимы колонок (`Номенклатура`, `item_cnt_day`,
`Продано, шт.`), поиск строки шапки в первых 20 строках (выгрузки 1С кладут
сверху 3–5 служебных строк — это и есть типовая причина ошибки «колонки не
найдены»), выбор листа с наибольшим числом распознанных колонок.

**Слой 2 — типы.** Даты: Excel serial (`45890`), ISO, `31.12.2025`, `31/12/25`,
«31 декабря 2025». Числа: `1 234,56`, `1,234.56`, неразрывный пробел,
`12 шт`, `—`, `н/д`.

**Слой 3 — логика.** Возвраты (отрицательные продажи) → 0 с флагом.
Дубли «дата+товар» → суммируются. Похожие наименования («Молоко (1 литр)» и
«Молоко(1 л)») → склеиваются. Пропущенные даты → дозаполняются нулями:
для временного ряда пропуск строки означает «продали 0», а не «нет данных».
Выбросы → винзоризация по MAD, не удаление.

**Слой 4 — цензурированный спрос.** День, когда продажи = 0 **и** остаток = 0,
это не «спроса не было», а дефицит: спрос был, товара не было. Если скормить
такие дни модели как честные нули, она научится систематически занижать спрос —
и система начнёт усугублять out-of-stock вместо того чтобы его лечить.
Такие дни помечаются и исключаются из расчёта статистик.

**Слой 5 — отчёт.** Машиночитаемый (`report.to_dict()` → JSON для интерфейса)
и текстовый (`report.to_text()` → кнопка «скачать лог», скриншот в курсовую).

## Страховой запас: квантили вместо коэффициента 1,65

Учебная формула `SS = 1.65 × σ × √L` предполагает нормальное распределение
спроса, которого у штучных товаров нет и близко: много нулей, редкие всплески,
асимметрия. Вместо этого обучаются две модели — на квантиль 0.5 и 0.9 —
и страховой запас берётся как их разность:

```
SS  = q90(спрос за L) − q50(спрос за L)
ROP = q50(спрос за L) + SS
Q   = q90(спрос за L + R) − остаток − товар в пути
```

Распределение берётся из самих данных, а не из предположения о его форме.
На защите это отдельный сильный пункт.

## Метрики: WAPE, а не только MAPE

`MAPE = mean(|y − ŷ| / y)` взрывается при y близком к нулю: день с продажей
1 шт и прогнозом 3 шт даёт вклад 200%. У сезонных товаров (персики зимой)
таких дней много. `WAPE = Σ|y − ŷ| / Σy` устойчив к нулям и читается как
«ошиблись на N% от оборота». Считаем обе: MAPE — потому что он в SMART-цели,
WAPE — потому что он честный.

## Автоматический отбор товаров: классификация спроса

Не всякий товар поддаётся прогнозированию. Молоко продаётся каждый день
примерно одинаково; коллекционный брелок — «0, 0, 0, 0, 4, 0, 0, 0, 3».
Модель, которой скормили второй ряд, увидит редкий всплеск и заложит
страховой запас «на такой случай» — деньги замораживаются, экономический
эффект уходит в минус.

Ручной порог по среднему объёму («брать товары от N шт/день») эту задачу
не решает: товар может продавать 6 шт/день в среднем и при этом две трети
дней простаивать. Такой порог его пропустит.

Система классифицирует каждый товар по методике **Syntetos-Boylan-Croston**
(`src/demand_classes.py`) по двум независимым признакам:

- **ADI** — средний интервал между продажами (регулярность)
- **CV²** — квадрат коэффициента вариации размера продажи (стабильность объёма)

|  | CV² < 0.49 | CV² ≥ 0.49 |
|---|---|---|
| **ADI < 1.32** | `SMOOTH` — ML-прогноз | `ERRATIC` — ML + увеличенный страховой запас |
| **ADI ≥ 1.32** | `INTERMITTENT` — правило min/max | `LUMPY` — закупка под заказ, прогноз не строится |

Классификация применяется **везде и всегда**, а не только при подготовке
датасета: при загрузке файла пользователем товар с хаотичным спросом
получает режим `minmax` независимо от того, сколько у него истории.
В `inventory.py` для него считается скромный страховой запас (одна типичная
партия вместо редкого пикового всплеска), а в бэктесте такие товары
исключаются из расчёта эффекта — система не обещает их прогнозировать,
поэтому и мерить её на них некорректно. Число исключённых позиций всегда
показывается в сводке.

Дни дефицита (`is_censored`) исключаются из расчёта ADI: иначе товар,
которого не было на складе по вине самой закупки, ошибочно попадёт
в «прерывистые» и система перестанет его прогнозировать.

Дополнительно считается ABC-анализ по обороту. Сочетание «группа A +
непрогнозируемый спрос» выводится отдельным предупреждением: товар важный,
но автоматика с ним не справится — нужен человек.

Отключается флагом `--no-classify` у `prepare_1c.py` и параметром
`respect_demand_class=False` у `forecast()`.

## Экономика из данных и автонастройка запаса

Система не спрашивает у пользователя то, что уже лежит в его файле.
Если в выгрузке есть колонки с ценой продажи и закупочной ценой
(«Цена продажи», «Себестоимость», «Закупочная цена» и десяток других
написаний — см. `COLUMN_SYNONYMS`), экономика считается по реальным
цифрам магазина, а не по усреднённым допущениям. Цен нет — работают
значения по умолчанию, и это честно помечается в отчёте.

**Сколько держать страхового запаса — вопрос с точным ответом.**
Он выводится из экономики товара по модели газетчика (newsvendor):

```
Cu = цена продажи − закупочная цена        (цена нехватки)
Co = закупочная цена × ставка хранения × дни / 365   (цена излишка)

оптимальный уровень сервиса = Cu / (Cu + Co)
```

Смысл: если упущенная прибыль в 20 раз дороже хранения, спрос надо
закрывать с вероятностью ≈ 95%. Если маржа копеечная, а склад дорогой —
оптимум опускается, и большой запас становится убыточным.

Расчёт идёт **по каждому товару отдельно**, поэтому у товаров с разной
экономикой получается разный запас:

| Товар | Маржа | Уровень сервиса | Множитель запаса |
|---|---|---|---|
| Икра красная | 40% | 98% | × 1.61 |
| Молоко | 27% | 97% | × 1.42 |
| Сигареты | 8% | 86% | × 0.85 |

**Почему одной формулы мало.** Модель газетчика предполагает нормальное
распределение с бесконечными хвостами. В жизни спрос ограничен: начиная
с некоторого уровня запаса дефицит исчезает полностью, и дальнейшее
наращивание — чистые потери на хранении. Формула этого не видит.

Поэтому `economics.autotune_service_factor()` работает как гибрид:
теория задаёт точку отсчёта и границы поиска, а короткий бэктест на
истории пользователя (8 товаров, 60 дней — около 10 секунд) уточняет
ответ. Пользователь при этом не настраивает ничего.

Проверить, что автонастройка попадает в оптимум, можно скриптом
`scripts/tune_service.py` — он строит полную кривую перебором и
сравнивает с автоматическим выбором. Запускать не обязательно, это
материал для пояснительной записки.

## Сайт, подключённый к модели

```bash
python scripts/serve.py          # затем открыть http://localhost:8000
```

`scripts/serve.py` написан на стандартной библиотеке — ставить ничего
не нужно. Он отдаёт и сайт, и API с одного адреса, поэтому настраивать
ничего не требуется. `api/main.py` (FastAPI) остаётся для продакшена:
логика у них общая, оба вызывают одни и те же функции из `src/`.

**Сайт работает и без сервера.** Если модель недоступна, страница
честно пишет об этом и считает прогноз сама, старой формулой — её
можно открыть двойным кликом и показать где угодно без установки.
Это не запасной вариант на всякий случай, а осознанный режим
демонстрации.

Что появляется, когда сервер есть:

| | Без сервера | С сервером |
|---|---|---|
| Прогноз | среднее за окно | градиентный бустинг |
| Страховой запас | норматив 1.65σ | доверительный интервал + экономика товара |
| Очистка данных | базовая | пять слоёв + отчёт на экране |
| Классы спроса | нет | бейдж у каждого товара |

Адрес API определяется автоматически: тот же хост, откуда открыта
страница, либо `localhost:8000` для файла. Переопределяется параметром
в адресной строке: `index.html?api=http://192.168.1.50:8000`.

Интеграция вносится в сайт скриптом `scripts/patch_web.py` — он
идемпотентный и правит исходный файл по якорям, поэтому обновить
дизайн сайта можно, просто положив новую версию в `web/index.html`
и запустив патч заново.
